# Пользователи: модель, миграция, проверки, API

Спека тикета [#168](https://github.com/SBKubric/sane-3x-ui/issues/168) (родитель [#167](https://github.com/SBKubric/sane-3x-ui/issues/167), раздел «Модель»). Термины по [CONTEXT.md](../../CONTEXT.md): **пользователь**, **клиент**, **подписка**, **технический пользователь**, probe account. Совместимость с upstream — [ADR 0002](../adr/0002-additive-upstream-compatibility.md). Бот ([#169](https://github.com/SBKubric/sane-3x-ui/issues/169)) зовёт `SubUserService` напрямую, страница панели ([#170](https://github.com/SBKubric/sane-3x-ui/issues/170)) — через HTTP API §6.

## 1. Модель

Новая таблица `sub_users`, модель `database/model/sub_user.go` (`SubUser`). Имя `users` занято upstream-таблицей администраторов панели (`model.User`), а upstream-модели не трогаем.

| поле | тип | назначение |
|---|---|---|
| `sub_id` | string, PK | подписка пользователя; у технических — зарезервированный ключ |
| `name` | string, unique | имя; уникально без учёта регистра (проверяет сервис) |
| `tg_id` | int64 | Telegram пользователя — главный: уникален, если не 0, пишется всем его клиентам (§11) |
| `comment` | string | |
| `contact_email` | string | почта пользователя для связи, необязательная ([#193](https://github.com/SBKubric/sane-3x-ui/issues/193)); не xray email |
| `created_at`, `updated_at` | int64, мс | служебные |

- **Клиент** принадлежит пользователю через subId: у xray-клиента — поле `subId` в `settings.clients` inbound'а, у AWG/WG-клиента — связка `tunnel_client_subs` ([tunnel-subscription.md](tunnel-subscription.md) §2, модель `database/model/tunnel_subscription.go`, FK на `tunnel_clients.uuid` с `ON DELETE CASCADE`). Своих строк клиентов у пользователя нет: принадлежность каждый раз читается с клиентов, поэтому клиент, записанный путём, который о пользователях не знает (сохранение inbound'а целиком, импорт, копирование клиентов), всё равно попадает к нужному пользователю.
- **Технические пользователи** хранятся под ключами `@robot` и `@monitoring`. Ключ с `@` не бывает subId'ом: проверки §4 его отвергают.
  - `robot` — без подписки. Ему принадлежат xray-клиенты с пустым subId и AWG/WG-клиенты без связки; их данные не меняются.
  - `monitoring` — probe accounts (имя с префиксом `probe-`) и всё, что несёт текущий probe subId (`monProbeSubId`). Probe subId появляется при первом ensure и сбрасывается при удалении probe set, поэтому он не ключ строки, а читается из настройки: смена subId не требует переписывать таблицу. AWG probe-пиры привязываются к probe subId при каждом ensure (`linkTunnelProbes`).
- MTProto-клиенты в пользователей не входят: у них своя таблица, в подписке их нет.

## 2. Технические пользователи

- Их нельзя удалить, включить/выключить, добавить им протокол, назначить им клиента: все операции записи `SubUserService` отвечают «technical user and cannot be changed by hand».
- Имена `robot`, `monitoring` (без учёта регистра) и любое имя с префиксом `probe-` не может занять ни пользователь, ни клиент.
- В `monitoring` вручную ничего не добавить: probe-имена и probe subId отвергают guards probe accounts и проверки §4; клиентов туда кладёт только `MonitoringService.EnsureProbeSet`.

## 3. Миграция

`SubUserService.Sync`, post-migrate hook (`database.RegisterPostMigrate`) — выполняется при каждом старте.

1. Создаёт `robot` и `monitoring`, если их нет.
2. Обходит клиентов по порядку: xray-клиенты по возрастанию id inbound'а в порядке `settings.clients`, затем AWG, затем WG по id.
3. Для каждого subId без пользователя создаёт пользователя с именем по email первого клиента; при совпадении (без учёта регистра) или зарезервированном имени — `-2`, `-3`… Пустой email — имя `user`.
4. Пропускает клиентов `robot` и `monitoring` (§1): probe subId пользователем не становится.
5. Даёт пользователю без tgId согласованный tgId его клиентов (§11).

Существующих клиентов миграция не читает на запись: не переименовывает, subId не выдаёт, дубликаты имён старых данных оставляет как есть. Повторный запуск ничего не меняет, переименованного вручную пользователя обратно не переименовывает.

Тот же `Sync` выполняется в начале каждого вызова `SubUserService`. Так соблюдается инвариант «у каждого subId есть пользователь» для клиентов, добавленных через панель или API с новым subId: пользователь с именем первого клиента появляется до того, как его кто-то увидит. Отдельного hunk'а для автосоздания в путях добавления нет.

## 4. Проверки

Одна функция — `SubUserService.ValidateClientWrites(ClientWrite…)`. Правила действуют только на новые записи:

- **Имя клиента уникально по всем протоколам** — среди email'ов xray-клиентов и туннельных клиентов, без учёта регистра, в том числе внутри одного запроса. Проверяется только новое имя: клиент со старым дублирующимся именем редактируется, пока имя не меняют. Ошибка называет занявшего: `client name "ivan-awg" is already taken: AmneziaWG client of user petr`.
- **Имена технических пользователей** не бывают именами клиентов: `name "robot" is reserved for a technical user`.
- **subId принадлежит одному пользователю**: ключ технического пользователя не subId (`subId "@robot" is reserved…`); probe subId — `monitoring` (`subId "…" belongs to technical user monitoring`); запись, которая называет пользователя (бот, API пользователей), не может взять чужой subId: `subId "s1" belongs to user petr`. Запись с существующим subId без имени пользователя — так панель добавляет протокол в существующую подписку — разрешена: клиент становится клиентом этого пользователя.

Где вызывается:

| путь | место |
|---|---|
| добавление xray-клиента (`AddInboundClient`, в т. ч. бот, копирование клиентов) | внутри форкового guard'а `rejectNewProbeClients` (`monitoring_probe.go`) — в `inbound.go` hunk'а для add нет |
| обновление xray-клиента (`UpdateInboundClient`) | один hunk в `inbound.go` рядом с форковыми probe-guard'ами |
| AWG/WG API `client/add`, `client/update/:id`, `client/updateByUuid/:uuid` | hunk'и tunnel subscription §4 в `tunnel_controller.go`, помощники в `tunnel_controller_sub.go` (`ValidateTunnelClientWrite`) |
| `SubUserService` | до первой записи (`planClients`) |

Сохранение inbound'а целиком (`AddInbound`/`UpdateInbound`) проверок пользователей не проходит — как и в родителе; принадлежность таких клиентов подхватывает `Sync`.

## 5. `SubUserService`

`web/service/sub_user*.go`. Пользователь адресуется ключом: subId, у технических — `@robot`/`@monitoring`.

| метод | что делает |
|---|---|
| `List()` | все пользователи, технические первыми, затем по имени |
| `Get(key)` | пользователь с клиентами |
| `Find(q)` | по имени пользователя, subId или имени клиента; результат один, иначе ошибка (не найден / имя клиента у двух пользователей) |
| `Search(q)` | нечёткий поиск бота и страницы (§5.1): до 20 пользователей, лучшие первыми |
| `Inbounds()` | inbound'ы, где пользователю можно создать клиента: vless, vmess, trojan, shadowsocks, amneziawg |
| `Create(SubUserCreate)` | пользователь и клиент в каждом из `inboundIds`; subId генерируется (16 символов), если не задан. Отказ, если `contactEmail` — не адрес почты или `tgId` уже у другого пользователя |
| `CheckNewName(name)`, `CheckNewTgId(tgId)`, `CheckContactEmail(email)` | проверки `Create` по одной, для шагов диалога бота: имя свободно и не зарезервировано; Telegram id не принадлежит другому пользователю (его `tg_id` или tgId его клиента, правило 1:1 карты #178); почта — голый адрес с доменом через точку, до 254 символов |
| `AddProtocol(key, inboundId, linkExisting)` | клиент ещё в одном inbound'е; параметры копируются с xray-клиента пользователя, иначе с AWG-клиента |
| `RemoveProtocol(key, inboundId)` | удаляет клиента пользователя в inbound'е; после последнего пользователь остаётся со своим subId |
| `SetEnable(key, enable)` | включает/выключает всех клиентов пользователя |
| `Telegram(key)`, `SetTelegram(key, tgId)`, `UnlinkTelegram(key)` | Telegram пользователя, «Назначить», «Отвязать» (§11) |
| `Delete(key)` | удаляет клиентов и пользователя |
| `Assign(key, clientName)` | отдаёт клиента `robot` пользователю: xray-клиенту пишет subId, AWG/WG-клиента привязывает; имя не меняется |
| `ValidateClientWrites`, `ValidateTunnelClientWrite` | проверки §4 |

- **Имя клиента** — `<пользователь>-<remark inbound'а>` (`SubUserClientName`): буквы, цифры и `. _ @` сохраняются, любая другая последовательность символов — один `-`, края `-`/`.` срезаются. Пустой remark заменяется протоколом.
- **Лимиты** (`totalGB` в байтах, `expiryTime` в мс, отрицательный — отсчёт с первого подключения, `limitIp`, `reset`) у каждого клиента свои: 50 ГБ на VLESS и 50 ГБ на AWG дают до 100 ГБ. В представлении пользователя `total` — сумма лимитов (0, если хоть один безлимитный), `expiryTime` — общий срок (0, если сроки разные), как `Subscription-Userinfo` у `/sub`. Как сумма сложилась, бот и страница подписки говорят **общим лимитом** (§16).
- **Атомарность.** Всё проверяется до первой записи (inbound существует и поддерживается, у пользователя там ещё нет клиента, имена свободны). Затем строка пользователя, затем клиенты по порядку: xray — через `AddInboundClient`, AWG — `AwgService.AddClient` + связка. Если клиент не создался, уже созданные откатываются в обратном порядке: settings xray-inbound'а восстанавливаются из снимка, строки трафика и IP удаляются, xray-пользователь снимается с работающего xray; AWG-пир удаляется (связка уходит каскадом); строка пользователя удаляется.
- **AWG-клиент с тем же именем уже есть:**
  - без связки — ошибка `SubUserConflict{code: "awg_linkable", client}`; бот или страница спрашивают оператора и повторяют запрос с `linkExisting: true`, тогда существующий клиент привязывается вместо создания нового;
  - привязан к другому пользователю — ошибка проверки §4, ничего не создаётся.
- **Пустой inbound.** Панель не оставляет xray-inbound без клиентов (`no client remained in Inbound` в upstream). `RemoveProtocol` и `Delete` проверяют это заранее и отказывают с именем inbound'а, ничего не удалив.
- Если нужен перезапуск xray (клиент не встал через API у включённого inbound'а), сервис сам ставит флаг `SetToNeedRestart`.
- Все записи сериализованы мьютексом (`subUserMu`); проверки §4 его не берут, поэтому операции сервиса проходят через guarded-пути панели.

### 5.1. Поиск

`Search(q)` (`web/service/sub_user_search.go`, решение [#186](https://github.com/SBKubric/sane-3x-ui/issues/186) п. 6, тикет [#211](https://github.com/SBKubric/sane-3x-ui/issues/211)) — одно поле, без учёта регистра, пробелы по краям не считаются.

- **Поля:** имя пользователя, subId (у технических — нет: `@robot` не subId), почта пользователя (`contact_email`), `@ник` Telegram, имена клиентов (xray email, имя AWG/WG-клиента). Технический пользователь находится по имени и по своим клиентам.
- **Ранг поля**, лучший первым: точное совпадение → начало поля → подстрока → опечатки. Пользователь получает лучший ранг среди своих полей; внутри ранга — меньше правок, затем имя.
- **Опечатки** — расстояние Левенштейна по символам: 1 правка в слове до 5 символов, 2 — в более длинном. Сравниваются и поле целиком («ivanpetrov» ↔ «ivan-petrov»), и слова: каждое слово запроса должно найти слово поля (слова — по любым символам, кроме букв и цифр, порядок не важен).
- **Короткие запросы:** один символ — только точно или начало поля; подстрока — с двух символов; опечатки — с трёх (слово запроса короче трёх символов должно быть началом слова поля).
- **Цифры:** tg_id — пользователя или его клиента — совпадает только целиком. Запрос из одних цифр опечаток не прощает (tg_id на цифру дальше — другой человек), но находит имена и subId, где эти цифры стоят.
- **`@ник`** — ник Telegram-аккаунта (§11), на который указывает `sub_users.tg_id` пользователя; сравнивается как остальные поля (точно, начало, подстрока, опечатки), с `@` или без. Запрос с `@` ищет только по никам. Ники берёт `TgAccountService.UserNicks` (`sub_user_search_nick.go`) одним запросом; аккаунт без пользователя никого не находит, ник, перешедший к другому аккаунту, находит пользователя нового аккаунта.
- **До 20 результатов** (`SubUserSearchLimit`). Индекс читается один раз, как в `List`; сопоставление — в памяти (3000 пользователей: ~45 мс, дешевле `List`).

## 6. HTTP API

`web/controller/sub_user_controller.go`, группа `/panel/api/users` (одна строка в `APIController.initRouter`), за сессией панели: без неё — 404, как у остального `/panel/api`. Ответ — обычный конверт `{success, msg, obj}`; при отказе `msg` — сообщение сервиса, при `awg_linkable` в `obj` лежит `{code, client}`, при `tg_owned` — `{code, tgId, owner, ownerSubId}`, при `tg_nick_unknown` — `{code}` (§11). Тела разбираются строго: неизвестное поле — отказ.

| метод и путь | тело | ответ `obj` |
|---|---|---|
| `GET /list` | — | `[]SubUserView` |
| `GET /inbounds` | — | `[]{id, remark, protocol, enable}` |
| `GET /get/:subId` | — | `SubUserView` |
| `GET /find?q=` | — | `SubUserView` |
| `GET /search?q=` | — | `[]SubUserView` — `Search` §5.1, лучшие первыми; никого — `[]` |
| `POST /create` | `{name, subId?, tgId, tgNick?, comment, contactEmail?, inboundIds[], totalGB, expiryTime, limitIp, reset, linkExisting}` | `SubUserView` |
| `POST /addProtocol/:subId` | `{inboundId, linkExisting}` | `SubUserView` |
| `POST /removeProtocol/:subId` | `{inboundId}` | `SubUserView` |
| `POST /enable/:subId` | `{enable}` | `SubUserView` |
| `POST /del/:subId` | — | — |
| `POST /assign/:subId` | `{client}` — имя клиента `robot` | `SubUserView` |
| `GET /telegram/:subId` | — | `SubUserTelegram` (§11) |
| `POST /setTelegram/:subId` | `{tgId, tgNick?}` | `SubUserView` |
| `POST /unlinkTelegram/:subId` | — | `SubUserView` |
| `POST /moveTelegram/:subId` | `{tgId}` | `SubUserView` — «Перенести сюда» (§11) |
| `GET /telegramInvite/:subId` | — | `TgInviteView` или `null` (§11) |
| `POST /telegramInvite/:subId` | — | `TgInviteView`: открытое приглашение или новое |
| `POST /reissueTelegramInvite/:subId` | — | `TgInviteView`: новое, прежнее отозвано |
| `POST /broadcastLinks` | — | `{id, recipients, noTelegram}` — рассылка ссылок всем (§13); бот не запущен — отказ |

`SubUserView` — `{subId, name, tgId, comment, contactEmail, createdAt, updatedAt, technical, enable, up, down, allTime, total, expiryTime, tgConflict, clients[]}`; `enable` — включён хоть один клиент. Клиент — `{kind: xray|awg|wg, inboundId, inboundRemark, protocol, name, key, subId, enable, up, down, allTime, totalGB, expiryTime, limitIp, tgId, reset, lastOnline}`; `key` — идентификатор клиента в его собственном API (id/password/email/auth у xray, uuid у туннеля).

## 7. Связь с tunnel subscription

Из [tunnel-subscription.md](tunnel-subscription.md) здесь реализованы модель связки (§2), её половина сервиса (`Set`/`Clear`/`SubIdsByUUIDs`, §3) и `subId` в AWG/WG API (§4). Маршрута `/tun/<subId>`, `Userinfo`, TTL-кэша, настроек, UI панели и proxy front (§3 остальное, §5–§8) пока нет: пока их нет, AWG-клиент пользователя принадлежит его подписке в панели и боте, но в `/sub` и `/tun` не отдаётся.

## 9. Страница панели

Тикет [#170](https://github.com/SBKubric/sane-3x-ui/issues/170). Страница `/panel/users` (`web/html/users.html`, обработчик в `web/controller/sub_user_page.go`, одна строка в `XUIController.initRouter`), пункт меню «Пользователи» после «Мониторинга» (один hunk в `aSidebar.html`). Своих данных у страницы нет: всё читается и меняется через API §6.

- **Таблица:** имя; почта пользователя (колонка «Почта», `contactEmail`, «—», если нет); теги протоколов — по одному на inbound, где у пользователя есть клиенты (`remark · протокол`, `×N`, если клиентов там несколько); трафик — использовано / лимит из `SubUserView` (`up + down` / `total`, 0 — «без лимита»); срок — общий срок клиентов или «у клиентов разный» (`expiryTime` представления 0 и для «бессрочно», и для «разный», поэтому страница смотрит на клиентов); ссылка подписки `subURI + subId` с копированием и QR; переключатель вкл/выкл.
- **Поиск:** одно поле над таблицей. Через 250 мс после ввода (или по Enter) страница спрашивает `GET /search?q=` (§5.1) и показывает найденных в порядке сервиса; ответ на устаревший запрос отбрасывается, после изменения поиск повторяется. Пустое поле — все пользователи.
- **«xray email».** Подпись поля `email` клиента в панели — «xray email» (ключ `pages.inbounds.email` во всех языках): модалка клиента, таблица клиентов в форме inbound'а, info-модалка, копирование клиентов, массовое добавление (поле способа генерации). Имена полей в API и JSON не меняются ([#186](https://github.com/SBKubric/sane-3x-ui/issues/186) п. 7).
- **Технические пользователи** помечены тегом; у них нет переключателя, удаления, ➕/➖ и ссылки. Кнопка клиентов открывает список клиентов пользователя; у `robot` у каждого клиента кнопка «Назначить пользователю», `monitoring` только для чтения.
- **Создание:** имя, галочки inbound'ов из `GET /inbounds` (включённые отмечены сразу), лимит трафика в ГБ, срок (дата), лимит IP, Telegram ChatID, комментарий — одни на всех клиентов. Ответ `awg_linkable` превращается в вопрос «Привязать существующего AmneziaWG-клиента?»; «Привязать» повторяет запрос с `linkExisting: true`. То же в ➕.
- **➕** предлагает только inbound'ы, где у пользователя ещё нет клиента. **➖** и удаление спрашивают подтверждение. Отказ сервиса показывается его текстом (например, «inbound … would be left without clients»).
- **Модалка клиента на Inbounds:** под полем subId подсказка «Пользователь: <имя>» (`component/aSubUserHint.html`; hunk в `form/client.html` и подключение в `inbounds.html`). Владелец subId берётся из `GET /list`: subId пользователя и subId его клиентов (так probe subId показывает `monitoring`); пустой subId — `robot`, незнакомый — «новый» (после сохранения `Sync` создаст пользователя по имени клиента). Ошибки проверок §4 при сохранении приходят обычным путём панели: `jsonMsg` → toast «Something went wrong (<текст проверки>)».

Вид экрана задаётся его route — callback data, которая рисует его заново. «Назад» снимает route со стека; «Меню» стек очищает. Переход на route, который уже есть в стеке, обрезает стек до него: подтверждение возвращается к карточке, а карточка после действия ведёт туда же, куда вела раньше. Онлайн, Отчёты, Мониторинг, Сервер и Админка — экраны [#192](https://github.com/SBKubric/sane-3x-ui/issues/192), ниже.
- **«➕ Новый пользователь»** ([#193](https://github.com/SBKubric/sane-3x-ui/issues/193), `web/service/tgbot_screen_newuser.go`) — диалог на экране, по прототипу #185. Шаги (в заголовке «шаг N/5»):
  1. **имя** текстом; занятое или зарезервированное имя — ⚠️ с текстом отказа `CheckNewName` на том же шаге;
  2. **почта** пользователя текстом или «Пропустить ▶»; не xray email (тот генерируется), проверка `CheckContactEmail`;
  3. **протоколы**: галочки по `Inbounds()` (`✅ VLESS · <remark>`), включённые inbound'ы отмечены; нажатие меняет только кнопки; «Далее» без галочек — toast, шаг не меняется;

Пресеты: значение настройки, затем `100 ГБ · ∞` (у срока `90 дн. · ∞`), без повторов: настройка 100 ГБ даёт `100 ГБ · ∞`, настройка 0 — `∞ · 100 ГБ`. Выбранный отмечен `●`; «✏️ Своё значение» ждёт целое число от 0 до 999999 (0 — без лимита/срока). То же на шаге лимитов «⚙️ Одобрить с изменениями» (§12);
  5. **Telegram** ([#219](https://github.com/SBKubric/sane-3x-ui/issues/219), решение [#187](https://github.com/SBKubric/sane-3x-ui/issues/187)): кнопки «✏️ Ввести tg_id / @ник» (свой вид шага с «◀ Изменить»), «🔗 Создать ссылку-приглашение» и «Позже ▶»; tg_id или @ник можно прислать и прямо на шаге. Не число и не ник — ⚠️, ник, которого бот не видел, — ⚠️ «человек ещё не писал боту, отправьте ссылку-приглашение», tg_id другого пользователя — ⚠️ `CheckNewTgId` (перенос — из карточки, §11). С «Создать ссылку-приглашение» пользователь создаётся без Telegram, и вместо карточки на экране — его ссылка-приглашение (§11) с кнопкой «👤 <имя>» на карточку.

## 11. Telegram-аккаунт и главный tgId

Тикет [#210](https://github.com/SBKubric/sane-3x-ui/issues/210), решение [#186](https://github.com/SBKubric/sane-3x-ui/issues/186) (пункты 1–4, 8, 9).

- **Telegram-аккаунт** — таблица `tg_accounts` (`database/model/tg_account.go`, аддитивно по ADR 0002): `tg_id` PK, `username` (@ник без `@`), `first_name`, `last_name`, `last_seen` (мс). Запись создаёт или обновляет middleware бота (`noteSender`, `web/service/tg_account.go`, одна строка `h.Use` в `tgbot.go`) на каждое сообщение и нажатие любого отправителя — админа, клиента, новичка; боты пропускаются. Пишется не чаще раза в минуту на аккаунт, если ник и имя не менялись (память о последней записи — в процессе; после перезапуска первое обращение пишет). Ник уникален без учёта регистра: побеждает последний увиденный, у прежнего владельца ник стирается. Поиск по нику — `TgAccountService.ByUsername`.
- **Главный tgId — `sub_users.tg_id`**, уникален, если не 0: частичный уникальный индекс `idx_sub_users_tg_id … WHERE tg_id <> 0` создаёт post-migrate шаг `uniqueSubUserTgIds`; пользователи, которые делили один id до правила, теряют его и показывают конфликт. После каждого сохранения пользователя — `Create` (и привязка существующего AWG-клиента), `AddProtocol`, `Assign` из `robot`, `SetEnable`, `SetTelegram` — его tgId, если не 0, пишется всем его клиентам: xray — через `UpdateInboundClient`, туннельным — в `tunnel_clients.tg_id`. Новый клиент ➕ получает tgId пользователя, а не своего соседа. Пользователь без tgId клиентов не трогает: их id — конфликт. Наш код (`telegramSubUsers`, «Моя подписка», доступ не-админа) читает tgId только у пользователя; уведомления upstream и `/usage` по-прежнему читают клиентов.
- **Миграция** — шаг `Sync` (`adoptTelegramIds`), идемпотентна и пишет только `sub_users`: обычный пользователь без tgId берёт tgId клиентов, если среди ненулевых id клиентов ровно один и его нет ни у другого пользователя, ни у клиентов другого обычного пользователя (клиенты `robot` и `monitoring` не в счёт). tgId строкой (`"777"`) читается как число. Иначе `tg_id` остаётся 0, клиенты — со своими id.
- **Конфликт** — у клиента обычного пользователя tgId не 0 и не равен tgId пользователя (`SubUserView.tgConflict`). Два вида: клиенты не согласны между собой; id занят другим пользователем или есть у его клиентов. Так же помечается клиент, которому id поменяли в inbound'е после сохранения пользователя.
- **Разрешение.** `Telegram(key)` / `GET /telegram/:subId` — `{subId, name, tgId, account, conflict, candidates[]}`, кандидат — `{tgId, account, clients[], owner, ownerSubId, alsoOn[], assignable}`: id с клиентов пользователя, какие клиенты его несут, чей он (`owner` — пользователь с этим `tg_id`), у клиентов каких ещё пользователей он стоит. «Назначить <tg_id>» (`SetTelegram`) отказывает, если id — `tg_id` другого пользователя; id у чужих клиентов не мешает, тот пользователь остаётся в конфликте. «Отвязать Telegram» (`UnlinkTelegram`) — `tg_id = 0` у пользователя и у всех его клиентов; строка `tg_accounts` остаётся. Технических пользователей оба отвергают.
- **Бот** (`web/service/tgbot_users_telegram.go`, тексты — `[tgbot.tgaccount]`), только админам: в карточке строка «⚠️ Telegram: конфликт» и кнопка «⚠️ Telegram» (или «📱 Telegram» у пользователя с id) → экран `usr_tg <key>`: id и аккаунт пользователя, id клиентов с владельцами, «Назначить <tg_id>» (`usr_tga`) для свободных, «Отвязать Telegram» (`usr_tgu` → подтверждение `usr_tguc`). Отказ сервиса — над карточкой. Не-админ на любую из этих кнопок получает «No result».
- **Страница «Пользователи»**: тег «⚠️ Telegram: конфликт» у имени и кнопка Telegram открывают модалку с тем же списком, «Назначить» и «Отвязать Telegram» (с подтверждением). В модалке клиента под полем Telegram ChatID — «задаётся у пользователя».
- **Привязка** ([#219](https://github.com/SBKubric/sane-3x-ui/issues/219), решение [#187](https://github.com/SBKubric/sane-3x-ui/issues/187)) — три способа: tg_id, `@ник` и ссылка-приглашение. Пересылки сообщения и «поделиться контактом» нет: из-за приватности Telegram они ненадёжны.
  - **tg_id или @ник** (`TgAccountService.Resolve`, `web/service/sub_user_telegram_bind.go`): число — сам id; `@ник` (можно без `@`, регистр не важен; буква, затем буквы, цифры и `_`, всего 4–32) ищется в `tg_accounts`. Ника нет — отказ `tg_nick_unknown` «человек ещё не писал боту, отправьте ссылку-приглашение». API: `tgNick` рядом с `tgId` в `create` и `setTelegram`; если даны оба, они должны назвать один аккаунт.
  - **Правило 1:1.** Id другого пользователя `SetTelegram` отвергает отказом `tg_owned` с его именем и subId. «Перенести сюда» (`MoveTelegram`, `POST /moveTelegram/:subId`) после подтверждения отвязывает тот пользователь (он и его клиенты без id, как после «Отвязать») и привязывает этот — под одной блокировкой.
  - **Ссылка-приглашение** — таблица `tg_invites` (`database/model/tg_invite.go`, аддитивно): `token` (PK), `sub_id`, `created_at`, `expires_at` (+7 дней), `used_at`, `used_by`, `revoked`. Токен — 32 случайных байта в base64url, 43 символа из `[A-Za-z0-9_-]` (Telegram пропускает в `start` до 64). У пользователя одно открытое приглашение: `Invite` отдаёт его или делает новое, «🔄 Перевыпустить» (`Reissue`) отзывает все неиспользованные и делает новое. Ссылка — `https://t.me/<bot>?start=<token>`, имя бота — `getMe` работающего бота (кешируется на экземпляр бота); пока бот не запущен, ссылки нет (`TgInviteView.link = ""`, на странице и в боте — предупреждение), а токен уже есть. Сервис — `TgInviteService` (`web/service/tg_invite.go`); технические пользователи приглашений не получают.
  - **`/start <token>`** (`web/service/tgbot_start_invite.go`, одна вставка в `answerCommand`) — от любого, в личном чате, до проверки «админ или нет»; параметр, не похожий на токен, — обычный `/start`. `Redeem` под своим мьютексом: действующий токен → `SetTelegram` (tgId у пользователя и всех его клиентов), токен использован, человек видит «✅ Telegram привязан к вашей подписке» и строку со ссылкой на страницу подписки над «Моей подпиской» (без файлов, #245), в канал уведомлений — «🔗 <имя> привязал Telegram @nick». Повтор того же человека — снова подписка, без уведомления. Просрочен — «⌛ срок истёк, попросите новую»; использован другим, перевыпущен или неизвестен — «⚠️ уже использована или заменена»; Telegram человека — `tg_id` другого пользователя — «⚠️ Этот Telegram уже привязан к другой подписке, обратитесь к админу», ничего не переносится, приглашение остаётся открытым. Во всех трёх случаях админам — уведомление в канал с именами (кроме неизвестного токена); человеку — только текст и его собственное главное меню, имён чужих пользователей он не видит. Пользователь, получивший Telegram другим путём, делает своё приглашение недействительным.
  - **Бот** (`web/service/tgbot_users_invite.go`, тексты — `[tgbot.tginvite]`), только админам: в карточке без Telegram — «🔗 Ссылка-приглашение» (`usr_tgi`: ссылка, срок, «🖼 QR» `usr_tgq` — QR файлом, «🔄 Перевыпустить» `usr_tgr`) и «✏️ Ввести tg_id или @ник» (`usr_tge`, ждёт текст в состоянии `usr_tgset`; то же на экране `usr_tg`). Неизвестный ник — подсказка и кнопка ссылки, чужой id — «уже привязан к пользователю <имя>» и «➡️ Перенести сюда» (`usr_tgm` → подтверждение → `usr_tgmc`); чат ждёт следующей попытки. Не-админ на любую из этих кнопок получает «No result».
  - **Страница**: у имени пользователя без Telegram — тег «Telegram: не привязан», он открывает модалку Telegram; в ней — «🔗 Ссылка-приглашение» (ссылка, копирование, QR, срок, «🔄 Перевыпустить», без бота — предупреждение) и «✏️ Ввести tg_id или @ник» (поле и «Привязать»; неизвестный ник — предупреждение со ссылкой на приглашение, чужой id — подтверждение «Перенести сюда»). В окне создания — поле «Telegram: tg_id или @ник» и галочка «Создать ссылку-приглашение»: после создания открывается модалка Telegram нового пользователя с его ссылкой.

## 12. Заявки на подписку

Тикеты [#220](https://github.com/SBKubric/sane-3x-ui/issues/220) (заявитель) и [#221](https://github.com/SBKubric/sane-3x-ui/issues/221) (рассмотрение админом), решение [#188](https://github.com/SBKubric/sane-3x-ui/issues/188) с поправкой владельца к пункту 11 и двумя уточнениями (2026-09-30): капча относится только к боту, привязана только к Telegram-аккаунту (tg_id) и запоминается.

- **Модель** — таблица `sub_requests` (`database/model/sub_request.go`, аддитивно): `id`, `tg_id`, `comment` (≤ 200 символов), `status` (`pending` / `approved` / `rejected` / `cancelled` / `expired`), `created_at`, `decided_at` (мс), `decided_by` (админ; пусто для отмены и просрочки), `reason` (причина отказа). Блокировка — `tg_accounts.requests_blocked` (новая колонка; запись аккаунта ботом её не трогает). Сервис — `SubRequestService` (`web/service/sub_request.go`):
  - у аккаунта одна ждущая заявка (проверка и запись под одним мьютексом);
  - `ExpireDue` просрочивает заявки старше 14 дней, по одной; задача `SubRequestExpireJob` (раз в 10 минут, когда бот включён) пишет человеку «⌛ Ваша заявка от <дата> просрочена…»;
  - после отказа (`Reject`) новая заявка — через 7 дней от решения;
  - у аккаунта с пользователем (`telegramSubUsers`) и у заблокированного (`SetBlocked`) заявки нет;
  - `Create` требует, чтобы аккаунт прошёл капчу (`TgCaptchaService.Passed`). Прохождение запоминается: следующие заявки аккаунта идут без капчи, пока админ его не сбросит или не заблокирует аккаунт.
- **Капча ALTCHA** — только бота, к подпискам отношения не имеет: ни `subPath`, ни sub-сервера, ни subId. Ключ всего — tg_id из подписанной `initData`, и ничего больше. Пакет `captcha` (страница, виджет, задачи), сервис `TgCaptchaService` (`web/service/tg_captcha.go`), обработчик `web/controller/third_party.go`.
  - **Путь бота** — `/third-party/<secret>/` на фронте 443. `<secret>` — случайная строка из 24 латинских букв и цифр в настройке `tgThirdPartySecret`, создаётся при старте панели, если её нет (`EnsureTgThirdPartySecret`; у панели с цепочкой — новая ревизия). Вкладка Telegram, блок «Заявки на подписку», показывает путь только для чтения, адрес капчи и кнопку «Перевыпустить» (`POST /panel/setting/botPath`, `/panel/setting/botPath/renew`): новый секрет, старый путь сразу отвечает 404, у панели с цепочкой — новая ревизия в той же транзакции. Через общую форму настроек секрет не меняется.
  - **Маршрут.** Панель отвечает на `/third-party/<secret>/…` на своём порту, вне `webBasePath`, сессий и проверки домена (`controller.WithThirdParty` перед движком панели). Фронт `real` публикует путь на порт панели, как `mon/v1` (`nginx.Site.Bot`, лимит подписок), при любом `subsBehind443`. Звенья узнают путь из документа цепочки (`nextHop.thirdPartyPath`, [proxy-chain.md §3.3](proxy-chain.md)) и передают всё под ним следующему звену как есть. Чтобы запросы дошли по цепочке до панели, внутреннее звено должно звать `real` на 443 (`subsBehind443` на `real`, как на стенде): на sub-порту `real` пути бота нет.
  - **Сервер** — официальная Go-библиотека `github.com/altcha-org/altcha-lib-go` v1.0.0: задачи SHA-256 с HMAC-подписью, срок 10 минут, число до 200 000 — около секунды на телефоне. Ключ HMAC выводится из секрета панели (`secret`), одинаков после перезапуска. Каждая задача делается для одного tg_id: он лежит в `salt` (`tg=<id>`) под подписью, и решение проходит только с `initData` того же аккаунта. **Виджет** — `altcha` 2.3.0 из npm (`dist/altcha.umd.cjs`, MIT, воркер внутри), встроен в бинарник как `captcha/altcha.js`: без CDN. Версия 2.x выбрана под протокол Go-библиотеки; виджет 3.x — новый протокол, для которого Go-библиотеки нет.
  - **Страница** `/third-party/<secret>/captcha` — Telegram Mini App: кнопка `web_app` в боте, адрес — https хоста капчи (`BotPublicBase`, ниже). Нет https — бот пишет, что проверка недоступна. Страница берёт `initData` из фрагмента `#tgWebAppData=…` и закрывается событием `web_app_close` протокола Mini App — без `telegram-web-app.js` с telegram.org. Вне Telegram (без `initData`) — подсказка открыть её кнопкой в боте, виджета нет.
  - **Хост капчи** ([#243](https://github.com/SBKubric/sane-3x-ui/issues/243), с v1.9.1) — настройка `tgCaptchaHost`, вкладка Telegram, блок «Заявки на подписку» (выбор рядом с адресом капчи), и `x-ui setting -tgCaptchaHost <значение>` (заданное `""` — вернуть значение по умолчанию, флаг не задан — настройка не трогается):
    - `""` / `edge` (по умолчанию) — active edge: его фронт 443, иначе его https-порт; адрес следует за переключением edge. Нет active edge (в том числе без цепочки) — фронт 443 самой панели, как `panel`;
    - `panel` — фронт 443 самой панели, её домен из настроек nginx, иначе адрес из её IP-сертификата, и в цепочке тоже. Прежнее правило «адрес `real` за цепочкой не выдаётся никогда» этим заменено (решение владельца 2026-10-02): пользователи открывают Mini App, уже сидя под нашим VPN, и капча на edge в РФ открывается непредсказуемо — запрос уходит в туннель, выходит с `real` и идёт обратно на российский хост, по пути могут сработать правила ru-inside. У фронта `real` такого пути нет. Цена — адрес `real` в ссылке Mini App; фронту `real` нужен https на 443, и `real` должен быть доступен пользователям. В production выбрана панель;
    - имя звена (`[a-z0-9-]{1,32}`) — это звено реестра, по тому же правилу адреса, что у active edge. Путь бота отвечает на каждом звене — резервном edge и внутреннем тоже (`nextHop.thirdPartyPath` есть в каждом документе, `proxy/subserver_thirdparty.go` передаёт запрос внутрь, не глядя на роль), поэтому звеньям ничего менять не нужно. Звено с именем `edge` или `panel` так не выбрать.
    - Выбранный хост, который капчу отдать не может — звена нет в реестре, оно ещё не вошло (`pending`) или уходит (`draining`), у него нет ни фронта 443, ни https-порта; у панели nginx выключен или нет ни домена, ни IP-сертификата, — даёт пустой адрес и предупреждение в лог панели. На другой хост бот молча не переходит: Telegram открывает Mini App только по https, и администратор должен видеть, что капча недоступна.
    - Настройка меняет только ссылку на капчу (`requestCaptchaURL` в боте, `captchaUrl` в `POST /panel/setting/botPath`). Подписки, их публичный адрес (`subPublicURL`), VPN-имя, витрина и прочие пути — как были.
  - **API.** `POST …/captcha/challenge` (`{initData}`) — задача для этого аккаунта; виджет зовёт его через свой `customfetch`. `POST …/captcha/verify` (`{initData, payload}`). `initData` проверяется HMAC по токену бота (`telegoutil.ValidateWebAppData`), `auth_date` не старше 15 минут и не больше чем на минуту в будущем; tg_id — `user.id` из неё. Ответы: `200` — пройдено; `403` — `initData` не нашего бота или несвежая; `400` — решение неверное, чужого аккаунта, просроченное или уже использованное. Неверный секрет или выключенный бот — пустой `404` на любом пути.
  - **Хранение** (аддитивно, `database/model/tg_captcha.go`): `tg_captcha` по tg_id — `passed_at` (мс, 0 — не пройдена или сброшена), `attempts` (решения с верной `initData`), `last_attempt_at`, `last_fail_at`; `tg_captcha_solutions` — подписи принятых решений с `expires_at` их задачи: решение принимается один раз, и после перезапуска тоже; истёкшие строки удаляются при следующей проверке.
  - Прохождение записывается, и экран чата этого аккаунта приводится к шагу комментария (`requestCaptchaPassed`, в фоне; админам — нет). Есть ли у аккаунта пользователь, ждущая заявка или блокировка — решает бот (`requestNew`), не капча.

## 13. Рассылка обновлённой ссылки

Тикет [#222](https://github.com/SBKubric/sane-3x-ui/issues/222), решение [#214](https://github.com/SBKubric/sane-3x-ui/issues/214). Код — `web/service/sub_link.go` (детекторы), `sub_link_broadcast.go` (очередь, отчёт, журнал), `tgbot_sub_link.go` (вопрос и экраны), `web/job/sub_link_watch_job.go`, `web/controller/sub_user_link_controller.go`. Таблицы свои, аддитивные (ADR 0002): `sub_link_knowns`, `sub_link_broadcasts`, `sub_link_deliveries` (`database/model/sub_link.go`).

- **Детекторы.** Ссылка умирает при смене активного edge (host override), пути подписок (`subPath`), адреса или порта фронта, публичного адреса подписок (#224) и subId пользователя. Все пять видны в одном месте — в ссылке, которую панель выдаёт сейчас (`subscriptionURLs`), поэтому места, где они меняются, не перехватываются. Раз в 30 секунд (`SubLinkWatchJob`, при включённом боте) детектор сравнивает для каждого человека — Telegram-аккаунта, который `sub_users.tg_id` пользователя, — ссылку, которую тот последний раз знал (`sub_link_knowns`, по `tg_id`), со ссылкой его пользователя сейчас. Причина — по тому, чем они различаются: другой хост, и новый — хост публичного адреса подписок, — публичный адрес (`public`; и когда в ту же минуту сменилось активное edge: ссылка называет адрес, а не edge); другой хост, который есть (или был) у edge цепочки или в legacy override, — активное edge; другой адрес, порт или схема — фронт; другой путь перед subId — путь подписок; другой subId (Telegram перенесли на другого пользователя, пользователя пересоздали) — subId. Смены, которые приложения подтягивают сами (ключи, SNI, путь XHTTP), ссылку не меняют и событием не считаются. Очищенный публичный адрес прежний адрес не помнит: причина — тот сервер, который ссылка называет снова (edge или фронт). Смена активного edge при заданном адресе ссылку не меняет — вопроса нет.
- **VPN-имя** (#225, §15) в ссылке подписки не видно, поэтому известная ссылка помнит ещё VPN-имя, которое называли ссылки VLESS человека (`sub_link_knowns.vpn_name`; пусто — без имени или при выключенном override), и host override, с которым он известен (`edge_host`; на него смотрит `Endpoint` AWG). Задали, сменили или очистили VPN-имя — смена у всех, причина `vpnName` (ссылка подписки та же, и без Telegram — в отчёт для ручной отправки); при выключенном override VPN-имя ссылки не меняет. Сменилось активное edge, а ссылка подписки та же (задан публичный адрес) — у человека только с xray-клиентами смены нет (VLESS идёт по VPN-имени или приложение само подтянет подписку через витрину), у человека с включёнными туннельными клиентами — причина `edge`: его `.conf` называет старое edge. Без публичного адреса ссылка подписки сама называет edge, и смена edge — смена у всех, VPN-имя или нет. Строка, записанная до #225 (`edge_host` NULL), молча берёт текущий host override.
- **Известная ссылка** пишется, когда человек впервые виден с пользователем (молча), когда админ ответил на вопрос (и «Да», и «Нет») и когда ссылка ему ушла. До ответа смена остаётся сменой — и после перезапуска панели. Человек, который больше ничей Telegram, забывается.
- **Без Telegram.** Если сменилась ссылка всей панели (не только subId), включённые пользователи без Telegram попадают в вопрос и в отчёт для ручной отправки.
- **Склейка и вопрос.** Набор смен должен простоять `subLinkQuiet` (2 минуты): шаги одного переключения дают один вопрос. Затем каждому админу в личку — «🔗 Ссылки на подписку изменились», что сменилось, «📵 Без Telegram: M» и «Разослать N пользователям?» с «✅ Да» / «✖ Нет»; N — включённые пользователи с изменившейся ссылкой. Без «Да» ничего не уходит. Вопрос — отдельное сообщение, не экран: `answerCallback` отдаёт его кнопки (`sl_yes`, `sl_no`) в `subLinkPress` до экрана. Отвечает первый, у остальных вопрос дописывается («✅ @admin разослал…» / «✖ Не рассылали»). Новая смена после вопроса — новый вопрос, старый удаляется, его «Да» отвечает «вопрос устарел». Если сменилось только у выключенных — вопроса нет, смена принимается молча.
- **Ручной запуск.** «⚙️ Сервер» → «📣 Разослать ссылки» (`s_slk`): сколько получат (включённые с Telegram) и сколько без Telegram, пять последних рассылок журнала, «📣 Разослать всем (N)» через подтверждение. Карточка пользователя с Telegram, включённого, — «📣 Отправить ссылку» (`slk_u`) через подтверждение, только ему. Страница «Пользователи» — кнопка «Разослать ссылки» с подтверждением, `POST /panel/api/users/broadcastLinks`; отчёт — всем админам.
- **Получатели** — обычные включённые пользователи с `sub_users.tg_id`; технические и выключенные — никогда. Ссылка уходит только владельцу подписки: на `tg_id` пользователя, не на tgId клиентов.
- **Сообщение** — одно, текстом ([#245](https://github.com/SBKubric/sane-3x-ui/issues/245), с v1.9.1; до того — фото с QR ссылки и следом `.conf` и их QR файлами): «🔗 Ссылка на подписку обновилась», ссылка и инструкция («обновите подписку в приложении; если не помогло — удалите и добавьте заново по этой ссылке»), кнопка «📱 Моя подписка» (`client_commands` — уже в списке доступа клиента, открывает его экран). Если хэш конфигов включённых туннельных клиентов пользователя (`subLinkConfHash`) отличается от последнего, о котором ему сказали (`sub_link_knowns.conf_hash`), в сообщении ещё строка «📄 Для AmneziaWG/WireGuard есть новый .conf: возьмите его в «📱 Моя подписка» → «📄 Мои конфиги»», и хэш запоминается — следующая рассылка её не повторит, пока `.conf` снова не сменится. Сами файлы человек берёт кнопкой. Так «📣 Отправить ссылку» только что созданному пользователю тоже уходит одним текстом.
- **Очередь.** Рассылки идут по одной (`subLinkRunMu`) в своей горутине; вызовы Bot API — через 40 мс (~25 в секунду); на 429 — пауза `retry_after` (до 5 повторов). 403 «blocked» — человек заблокировал бота: так и пишется в журнал.
- **Отчёт** — админу, который запустил (с API — всем админам): «✅ Отправлено», «❌ Не отправлено» с причинами («🚫 заблокировал бота» или описание Telegram), «📵 Без Telegram» списком (до 30 строк, дальше «…и ещё N») и «📋 Ссылки для ручной отправки» (`sl_man <id>`), если кто-то остался: ссылки (как они есть сейчас) всех, до кого рассылка не дошла.
- **Журнал**: `sub_link_broadcasts` — повод (`auto`, `all`, `user`, `api`), причины, кто запустил, счётчики, время начала и конца; `sub_link_deliveries` — каждый пользователь рассылки и итог (`sent`, `failed`, `blocked`, `no_telegram`, причина).
- **Доступ.** Все маршруты рассылки (`sl_*`, `s_slk*`, `slk_*`) — только админам: их нет в `clientCallbacks`, не-админ получает «No result».
- **Тесты:** `sub_link_test.go` (детекторы: edge через `SetActive`, путь, адрес и порт фронта, публичный адрес, subId; тихие изменения), `sub_link_prompt_test.go` (склейка, вопрос всем админам, «Да», «Нет», устаревший вопрос, доступ), `sub_link_broadcast_test.go` (очередь на поддельном Bot API: темп, 429, блокировка, отказ, строка о новом `.conf` только при смене, ни фото, ни файлов; отчёт и ссылки для ручной отправки; экраны сервера и карточки; доступ; тексты во всех языках), `web/controller/sub_user_link_controller_test.go` (API), `e2e/tests/users-link-broadcast.spec.ts` (кнопка страницы → сообщение человеку и отчёт админу через fakebot).

## 14. Публичный адрес подписок

Тикет [#224](https://github.com/SBKubric/sane-3x-ui/issues/224), карта SBKubric/sane-3x-ui-orchestrator#52 (решение 6). Настройка `subPublicURL` — вкладка «Подписка», «Публичный адрес подписок»; `entity.NormalizeSubPublicURL`, `web/service/setting_sub_public.go`.

- **Значение** — origin: `http`/`https`, хост (имя, IPv4 или IPv6 в скобках) и необязательный порт 1–65535; без пути (кроме `/`), запроса, фрагмента и учётных данных. Хранится нормализованным: схема и хост в нижнем регистре, без `/` в конце, без порта по умолчанию для схемы. Иначе сохранение отказывает («public subscription address must be …»). По умолчанию пусто.
- **Пусто** — ссылки ровно как без настройки.
- **Задано** — origin каждой выдаваемой ссылки подписки, поверх `subURI`/`subJsonURI`/`subClashURI`/`subTunURI`, host override (активного edge) и фронта; пути — собственные пути панели (`subPath`, `subJsonPath`, `subClashPath`, `subTunPath`), их и проксирует витрина подписок. Через него идут: ссылки и QR бота (`subscriptionURLs` — админ, клиент, рассылка §13), `defaultSettings` панели (страница «Пользователи», карточки и QR клиентов на «Inbounds»), ссылки страницы подписки sub-сервера (`BuildURLs`) и `Profile-Web-Page-Url` у `/sub`, `/json`, `/clash` (адрес запроса на публичном адресе) и `/tun` (страница `/sub/<subId>`). Свой `subProfileUrl` владельца по-прежнему важнее заголовка.
- **Звенья цепочки** узнают адрес из документа (`publicSubUrl`, [proxy-chain.md §3.3](proxy-chain.md)) и называют его в ссылках своей страницы, QR и `Profile-Web-Page-Url` вместо себя; сохранение нового адреса бампает ревизию.
- **Витрина ходит на edge одним адресом** за всех клиентов, поэтому её адрес ставится в доверенные адреса фронта (`frontTrustedAddrs`, [#228](https://github.com/SBKubric/sane-3x-ui/issues/228), [proxy-chain.md §5.12](proxy-chain.md)): иначе защита edge (30 запросов в минуту на адрес, бан после 10 промахов) упрётся в витрину целиком.
- **Не меняется** адрес внутри конфигов (VLESS, AWG `Endpoint`): это host override и VPN-имя ([#225](https://github.com/SBKubric/sane-3x-ui/issues/225), §15).
- **Рассылка** (§13): смена адреса — смена ссылки всей панели, причина `public`, один вопрос админам.
- **Тесты:** `web/service/setting_sub_public_test.go` (проверка и нормализация), `web/service/sub_public_links_test.go` (бот, `defaultSettings`), `sub/sub_public_test.go` (страница, заголовки, `subProfileUrl`), `web/service/sub_link_test.go` и `sub_link_prompt_test.go` (причина, один вопрос), `web/service/chain_document_test.go` (поле документа, ревизия), `proxy/subserver_public_test.go` (звено), `e2e/tests/sub-public-url.spec.ts` (поле настроек и ссылка на странице «Пользователи»).

## 15. VPN-имя и напоминание о продлении домена

Тикет [#225](https://github.com/SBKubric/sane-3x-ui/issues/225), карта SBKubric/sane-3x-ui-orchestrator#52 (решения 7 и 8). Код — `web/entity/vpn_name.go` (проверка), `web/service/setting_vpn_name.go` (настройки, `GetLinkOverride`), `web/service/vpn_dns.go` (DNSExit), `web/service/domain_expiry.go` (напоминание), `web/job/vpn_name_job.go`.

- **Настройки** — вкладка «Подписка», раздел «VPN-имя (DNSExit)». Для orchestrator — ключи и флаги CLI (`x-ui setting -<ключ> <значение>`; пустое значение очищает; `panel/setting/update` не годится: обнуляет непереданные поля):

  | Ключ (`AllSetting`, CLI) | Значение | По умолчанию |
  |---|---|---|
  | `dnsExitApiKey` | API-ключ DNSExit; секрет: форма и API видят `********` (сохранение маски ключ не трогает), CLI печатает только `(set)`/`(not set)` | пусто — DNSExit не вызывается |
  | `vpnName` | DNS-имя, например `vpn.example.com`: две метки и больше, буквы, цифры, дефис внутри; не IP. Хранится в нижнем регистре без точки в конце | пусто — выключено |
  | `vpnNameTtl` | TTL A-записи в минутах (как у DNSExit), 1–1440 | `5` |
  | `domainExpiry` | дата окончания регистрации домена, `YYYY-MM-DD` | пусто — без напоминаний |

  Состояние `domainExpiryReminded` (`<дата>:<этапы>`) — не настройка, в форме его нет.
- **Ссылки.** При включённом host override конфиги xray подписки — ссылки VLESS (и других xray-протоколов) в `/sub`, адрес в `/json` — называют VPN-имя вместо адреса активного edge (`SettingService.GetLinkOverride`, `SubService.configHost`); SNI, ключи и порт те же. Остаются по адресу edge (`GetProxyOverride`): ссылки подписки (HTTP-сторона фронта edge отвечает только по адресу без SNI, незнакомое имя ушло бы к target-соседу), `Endpoint` AWG/WG (вопрос карты, пока по IP), пробы мониторинга (идут на своё звено), `/clash` (override там не применялся и раньше). При выключенном override VPN-имя ничего не меняет. Звеньям оно не нужно: конфиги собирает панель, в документ цепочки не попадает.
- **A-запись.** `VPNNameService.Tick` раз в 15 секунд сравнивает адрес, на который должна указывать запись, — IPv4 активного edge (хост-IP или то, во что резолвится хост-имя; IPv6 без IPv4 — ошибка), — с тем, что последний раз записал или увидел, и при расхождении зовёт DNSExit: `POST https://api.dnsexit.com/dns/`, `Content-Type: application/json`, тело `{"apikey":"…","domain":"example.com","update":[{"type":"A","name":"vpn.example.com","content":"192.0.2.10","ttl":5}]}` (`domain` — зона, зарегистрированный домен по public suffix list; `name` — полное имя, DNSExit не дописывает домен к имени, которое им уже кончается). Ответ `{"code":0,"message":"…"}`: `0` — успех, `1` («проблемы при выполнении, не обязательно отказ») — тоже, с предупреждением в лог, остальные коды и не-2xx — отказ. Запись в DNSExit должна существовать (владелец заводит её один раз). Места, где переключается edge (кнопка, `/proxy`, API, `SetActive`), не перехватываются.
  - **Не чаще раза в 4 минуты** (требование DNSExit): серия переключений — один вызов, через 4 минуты после предыдущего, за edge, активное к этому моменту; вернулись туда, где запись уже стоит, — вызова нет.
  - **Отказ** — повтор через 4, 8, 16, затем каждые 30 минут; третий отказ подряд — одно сообщение в канал уведомлений («⚠️ VPN-имя …: DNSExit отказал N раза подряд (причина)»), первый успех после него — «✅ … снова указывает на active edge». Ключ в сообщения и лог не попадает.
  - **Сверка**: при старте и потом раз в час имя резолвится; указывает не туда (правили руками, потерянное обновление) — ставится снова. Сразу после обновления сверки нет час: кэши резолверов.
  - **Ничего не происходит** без ключа, без имени и без активного edge (`/proxy off` запись не трогает). Состояние — в памяти; после перезапуска первым делом сверка.
- **Напоминание о продлении** (продлить через API DNSExit нельзя). Раз в час (`DomainExpiryJob`, при включённом боте), по дате в часовом поясе панели: за 30 дней, за 7 дней и в день окончания — по одному сообщению в канал уведомлений («📅 Регистрация example.com заканчивается …»; домен — зона VPN-имени). Каждое — один раз на дату, отмечается в `domainExpiryReminded`, поэтому перезапуск не повторяет; новая дата — заново. Если панель впервые смотрит уже внутри окна (дату ввели за 5 дней), уходит только напоминание этого окна. Дата прошла — одно «закончилась N дн. назад». Без бота или канала ничего не отправляется и не отмечается: напоминание ждёт.
- **Рассылка ссылок** (§13): причина `vpnName`; смена edge при VPN-имени и публичном адресе — вопрос только о людях с туннельными клиентами.
- **Тесты:** `web/entity/vpn_name_test.go` (имя, дата, TTL), `web/service/setting_vpn_name_test.go` (настройки, маска ключа, сеттеры CLI, `GetLinkOverride`, зона), `web/service/vpn_dns_test.go` (поддельный DNSExit: запрос, предел 4 минуты и склейка, повторы и уведомления, сверка, без ключа/имени/edge), `web/service/domain_expiry_test.go` (даты на поддельных часах, перезапуск, без канала), `web/service/sub_link_vpn_name_test.go` (детектор), `sub/sub_vpn_name_test.go` (`/sub`, `/json`, `/tun`, пробы), `main_vpn_name_test.go` (CLI), `e2e/tests/vpn-name-settings.spec.ts` (поля настроек, маска ключа).

## 16. Общий лимит

[#247](https://github.com/SBKubric/sane-3x-ui/issues/247), с v1.9.1. Лимит трафика по-прежнему у клиента, по одному на протокол, а у пользователя — их сумма (§5). Чтобы «0/100 ГБ» у пользователя с двумя протоколами по 50 ГБ было понятно, бот и страница подписки говорят, как сумма сложилась. Правило одно (`subpage.QuotaText`, `subpage/quota.go`):

- один клиент — его лимит: «Общий лимит: 50 ГБ»;
- у всех один лимит — «Общий лимит: 100 ГБ (50 ГБ × 2 протокола)»;
- лимиты разные — «Общий лимит: 70 ГБ (VLESS 50 ГБ + AmneziaWG 20 ГБ)»;
- хоть один клиент без лимита — «Общий лимит: без ограничения».

Протокол называется полным именем (`VLESS`, `VMess`, `Trojan`, `Shadowsocks`, `Hysteria2`, `AmneziaWG`, `WireGuard`; `subpage.ProtocolTitle`); у протокола, который у двух клиентов, — с remark inbound'а: «VLESS (xhttp)» (`subpage.PartLabels`). Существительное после числа — по русскому правилу (протокол / протокола / протоколов); в английском и прочих языках — «protocols».

- **Бот** (`web/service/tgbot_quota.go`): строка «📊 Общий лимит: … · израсходовано 3.3 ГБ» (`tgbot.users.quota`) по всем клиентам пользователя, как их считает `SubUserView`, — сверху «📄 Мои конфиги» и в карточке пользователя у админа под статусом подписки (`tgbot.users.subStatus`: вкл, срок). У пользователя без клиентов строки нет. «Моя подписка» трафик не показывает. Списки («👥 Пользователи», найденные, отчёты) и «🔗 Show subscription» оставляют сумму «3.3/100 ГБ» (`tgbot.screen.userLine`, `tgbot.screen.subStatus`). Карточки `robot` и `monitoring` — прежняя строка трафика.
- **Страница подписки**: под блоком использования — «Общий лимит: …» (`data-testid="sub-quota"`) и строка на клиента: имя протокола, использовано / лимит (`sub-quota-part`, ∞ без лимита). «Использовано», «Лимит» и «Осталось» тогда считаются по этим клиентам. Клиенты — те, что на странице: xray-клиенты подписки во включённых inbound'ах с трафиком и лимитом их строки `client_traffics` (как `Subscription-Userinfo`), затем туннельные клиенты подписки, пока tunnel subscription включена.
- **Заголовок `Sub-Traffic-Breakdown`** (`subpage.TrafficPartsHeader`): звено рисует страницу по ответу следующего звена, поэтому клиенты идут по цепочке заголовком рядом с `Subscription-Userinfo`. Значение — base64 JSON-массива `[{"p":"vless","r":"xhttp","u":3221225472,"t":53687091200}]`: протокол inbound'а, remark (обрезан до 32 символов, у туннельных клиентов пуст), использовано и лимит в байтах (0 — без лимита). Панель ставит его на сыром ответе `/sub/<subId>` (xray-клиенты и туннели) и на непустом `/tun/<subId>` (туннели) — на тех ответах, где уже стоит `Subscription-Userinfo`; страница панели берёт клиентов напрямую. Не больше 32 клиентов и 2048 байт: длиннее заголовок не ставится, страница показывает одну сумму (фронт звена — nginx, его буфер заголовков ответа — 4 КБ). Звено копирует заголовок дальше вместе с `Subscription-Userinfo` (`passthroughHeaders`) и рисует по нему страницу (`pageUsage`, и для страницы одних туннелей). Приложения неизвестный заголовок не читают; ASCII. Сам `Subscription-Userinfo` не меняется: сумма xray-клиентов, как раньше.
- **Совместимость.** Звено v1.9.0 заголовок не знает, не передаёт и рисует страницу как раньше; звено v1.9.1 за панелью без заголовка (или с непонятным значением) — тоже. Разбивка на странице звена появляется, когда обновлены панель и все звенья до клиента.
